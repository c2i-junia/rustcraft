# Hub and hosted worlds Implementation Plan

**Goal:** Accounts on a central hub created from the game, servers that check players by a
hub certificate, and hosted worlds the hub starts on the VPS for trusted players.

**Spec:** `docs/superpowers/specs/2026-11-25-hub-design.md` (binding). Read the sections your
task names before starting.

## Global Constraints

- English for code, comments, docs and commits; Conventional Commits (`feat(hub): …`,
  `feat(server): …`), the subject a sentence in the repository's style, a body explaining
  what and why, **no trailer**.
- Doc comments in full sentences, tests named as sentences, sparse comments.
- Game workspace: `cargo fmt --all -- --check`, `cargo clippy --workspace --all-targets --
  -D warnings` and `cargo test --workspace -- --skip e2e::` are clean at each commit. Run the
  e2e and golden tests that touch what you changed (`cargo test -p client <filter>`; they need
  lavapipe, present on this machine). When a golden screenshot changes on purpose, update it
  with `UPDATE_GOLDEN=1` and look at the new image.
- Hub workspace (`hub/`): `cargo fmt --check`, `cargo clippy --workspace --all-targets -- -D
  warnings` and `cargo test --workspace` from `hub/`, clean at each commit. Tests that need
  Postgres read `HUB_TEST_DATABASE_URL`; `hub/scripts/test-db.sh` starts a throwaway
  `postgres:17` container on port 55432 and prints the URL.
- The hub uses the repository's pinned nightly toolchain (no `rust-toolchain.toml` in `hub/`).
- No tokio, reqwest or hyper in the game crates; HTTP in the game is `ureq` with rustls.
- `ClientToServerMessage` and `ServerToClientMessage` are append-only, with their pinning
  tests in `shared/src/messages/mod.rs`. Bump `PROTOCOL_ID` (44 today) once in the task that
  changes the wire format, and nowhere else.
- Each task updates what it makes outdated in `README.md`, `docs/ARCHITECTURE.md` and
  `CHANGELOG.txt` (under "Version: Unreleased", one line per player-visible change), and
  `hub/README.md` for the hub.
- Never commit secrets. Test keys are generated in the tests.

## Decisions

1. **One crate shared with the hub**, `crates/protocol` (package `rustcraft-protocol`), member
   of the game workspace and used by path from `hub/`. `shared/src/status.rs` moves there and
   `shared` re-exports it as `shared::status`.
2. **The hub reuses the game's nightly toolchain**: the root `.cargo/config.toml` has
   nightly-only options that cargo applies to `hub/` too.
3. **Password fields** are masked: if Bevy's `EditableText` has no masking, the Account screen
   shows a masked copy over the field and keeps the real text in the field (the implementer of
   task 11 checks Bevy 0.19 first and records which way was taken).
4. **The hub API is plain JSON over HTTPS**; binary values in JSON are hex (keys) or base64
   standard with padding (certificate bytes, signatures).
5. **Hosted worlds talk to the hub with a realm token**: 32 random bytes, base64url, stored
   hashed in `realms.token_hash`, renewed at each start and passed by the agent to the
   container in `RUSTCRAFT_REALM_TOKEN`.

## Lot 0 — server preparations

### Task 1: Save and exit on SIGTERM and Ctrl-C

The dedicated server has no signal handling: a `docker stop` or Ctrl-C loses up to 60 s of
play. On SIGTERM or SIGINT (Ctrl-C) a dedicated server must save the world and the online
players exactly as the autosave does (`server/src/world/save.rs`), let the writer finish
(`server/src/world/writer.rs`, dropping `WorldWriter` waits for queued writes), and exit with
status 0 within 10 s. A second signal while saving exits immediately with status 130.

- Use the `ctrlc` crate with its `termination` feature (handles SIGTERM too) in the server
  binary only (`server/src/main.rs`); it sets an `AtomicBool` that a system polls to save and
  send `AppExit`. Solo worlds (`is_solo`) keep their current exit path.
- Test: an integration test in `server/tests/` launches the built `server` binary
  (`env!("CARGO_BIN_EXE_server")`) on a free port in a temp game folder with a world, waits
  for its status port to answer, sends SIGTERM (`nix`/`libc` dev-dependency, Unix only),
  asserts exit status 0 within 10 s and that a player file or the world's `world.ron`
  modification shows the save happened (place a block through a `TestClient` before the
  signal if practical, else check `world.ron`'s modified time moved).
- Docs: README "Multiplayer" (stopping a server saves it), CHANGELOG.

### Task 2: Settings for a new world on the command line

`server/src/main.rs` gains, applied only when the world is created (no `world.ron` yet; a
warning is logged and the options ignored for an existing world):

- `--seed <u32>`; `--world-type <default|large-biomes|archipelago|single-biome>` with
  `--biome <name>` for `single-biome` (use the world types and biome names the game already
  has, see `WorldGenSettings` and the Singleplayer "New world" dialog; reuse their parsing if
  any); `--game-mode <survival|creative>`; `--difficulty <peaceful|easy|normal|hard>` (use the
  game's existing difficulty variants and names).
- `--max-players <1..=64>` (default 64) replacing the fixed `MAX_CLIENTS = 64`
  (`server/src/init.rs`), and reported as `max_players` by the status reply.
- Thread the values through `GameServerConfig` (`shared/src/lib.rs`) or a new struct, keeping
  solo worlds unchanged. Tests: a new world gets the seed, type, mode and difficulty given; an
  existing world keeps its own; a server with `--max-players 2` refuses a third client the
  same way a full server does today.
- Docs: README "Command-line options > Server", CHANGELOG.

## Lot 1 — protocol crate and hub

### Task 4: The protocol crate

Create `crates/protocol` (package `rustcraft-protocol`, edition 2021, no Bevy), add it to the
game workspace, depend on it from `shared`. Spec sections: "Repository layout", "Identity",
"Hub API".

- `status`: move `shared/src/status.rs` and its tests here unchanged; `shared` re-exports it
  (`pub use rustcraft_protocol::status;`) so no other game code changes.
- `identity`: `Certificate` and `SignedCertificate` exactly as the spec's fields; `sign(cert,
  &SigningKey) -> SignedCertificate`; `SignedCertificate::verify(&self, keys: &[(u8,
  VerifyingKey)], now: u64) -> Result<Certificate, CertificateError>` (checks the key id,
  signature, then decodes, then `issued_at <= now + 300` and `now < expires_at`);
  `join_message(nonce, server_key) -> Vec<u8>` and `verify_join(cert, nonce, server_key,
  signature)`; hex helpers for 32-byte keys. Use `ed25519-dalek` 2 (`rand_core` feature),
  `postcard` (alloc), `uuid` (serde, v4), `serde`, `base64`, `hex`.
- `api`: serde structs for every request and response of the spec's API table (accounts,
  sessions, recovery, me, password, certificates, revoked, profiles, realms, realm config,
  well-known), the `ErrorBody {error, message}` and an `ErrorCode` enum with the spec's codes
  serialized in snake_case.
- `pub const DEFAULT_HUB: &str = "https://hub.rustcraft.dev";`
- Tests: a signed certificate verifies; a flipped byte, an unknown key id, an expired or
  future certificate are refused with distinct errors; a join signature verifies only for its
  nonce and server key; API structs round-trip through JSON with the field names of the spec.

### Task 5: The hub skeleton

Create the separate project `hub/` (spec "Repository layout"): `hub/Cargo.toml` is both the
workspace (`members = ["."]` for now; `realm-agent` comes in task 14) and the package
`rustcraft-hub`; add `exclude = ["hub"]` to the root workspace. Dependencies: `axum` 0.8,
`tokio` (full), `sqlx` (postgres, runtime-tokio, tls-rustls, uuid, time, migrate, macros
off), `serde`, `serde_json`, `tracing`, `tracing-subscriber`, `clap` (derive, env),
`rustcraft-protocol` by path, `ed25519-dalek`, `rand`, `time`, `uuid`, `thiserror`/`anyhow`.

- `rustcraft-hub serve`: configuration from flags with env fallbacks: `--listen`
  (`HUB_LISTEN`, default `127.0.0.1:8080`), `--database-url` / `HUB_DATABASE_URL` or
  `HUB_DATABASE_URL_FILE`, `--public-url` (`HUB_PUBLIC_URL`), `--signing-key-file`
  (`HUB_SIGNING_KEY_FILE`, hex seed; `rustcraft-hub generate-key <path>` writes a new one with
  mode 0600), `--ip-secret-file` (`HUB_IP_SECRET_FILE`, for the sign-up HMAC), `--name`
  (`HUB_NAME`, default "Rustcraft"). Applies migrations at start (`sqlx::migrate!`).
- Migration `0001_accounts.sql`: the account tables of the spec's "Database" section (all but
  `realms` and `realm_members`), with the columns of the proposal (see the spec) and
  `CREATE EXTENSION IF NOT EXISTS citext`.
- Routes: `GET /.well-known/rustcraft-hub` (spec), `GET /healthz` (200 when the database
  answers). An `AppError` type renders the spec's error body and status codes.
- `hub/scripts/test-db.sh` (start/stop the test Postgres) and a test helper that creates a
  fresh database per test from `HUB_TEST_DATABASE_URL` (create a uniquely named database,
  run migrations, drop it after) and builds the router for `tower::ServiceExt::oneshot`
  calls. Tests: well-known lists the key and protocol id; healthz answers.
- `hub/README.md`: what the hub is, how to run it locally and test it.

### Task 6: Accounts, sessions and recovery

Spec sections "Accounts", "Rate limits", "Hub API". Routes `POST /v1/accounts`, `POST
/v1/sessions`, `DELETE /v1/sessions/current`, `DELETE /v1/sessions`, `POST /v1/recovery`,
`GET /v1/me`, `PUT /v1/me/password`, `DELETE /v1/me`.

- Username and password rules exactly as the spec (reserved names, `zxcvbn` score ≥ 2 with the
  username as user input). Argon2id `m=19456, t=2, p=1` via `argon2`, run in
  `spawn_blocking` behind a semaphore of `max(1, cores/2)` permits. Recovery codes in the
  spec's format. Session tokens and their SHA-256 storage, 90 days sliding expiry,
  `Authorization: Bearer`. Password change and recovery revoke the other sessions and all
  certificates (the `certificates` table exists from task 5). Delete as the spec says.
- Rate limits of the spec's table for sign-up (Postgres `signups`, HMAC of IPv4 or IPv6 /64
  with the ip secret; purge rows older than 30 days hourly), global sign-up cap, trusted ranges
  (`--trusted-ranges` / `HUB_TRUSTED_RANGES`, comma-separated CIDRs), failed logins per
  (username, IP) and per IP (in memory, `governor` or a small sliding window of your own). The
  client IP rule of the spec (trust `X-Forwarded-For` only from loopback).
- `audit_log` rows for signup, login_failed, login, password_changed, recovery_used,
  account_deleted.
- Tests (with Postgres): every validation error code; sign-up then log in; wrong password;
  the 11th sign-up from one IP in an hour is 429 with `Retry-After` while another IP passes;
  an IPv6 neighbour in the same /64 counts with it; the 6th failed login for a name is 429;
  recovery gives a new code and the old one stops working; changing the password logs out
  the other sessions; a deleted account cannot log in.

### Task 7: Certificates, revocation, profiles and the admin CLI

- `POST /v1/certificates` (session): validates the hex device key, stores a `certificates`
  row, signs a 7-day certificate (spec "Identity") with the hub key, 30 per hour per account.
  `GET /v1/revoked`: ids of revoked, unexpired certificates. `GET /v1/profiles?name=`:
  `{id, username}` of an active account, 404 otherwise.
- Suspended accounts: login and certificates answer 403 `forbidden` with the reason.
- `rustcraft-hub admin …` subcommands of the spec, working on the same database URL:
  `users` (table: name, roles, quota, status, created), `grant <user> host [--realms N]`
  (default 1), `grant <user> admin`, `revoke <user> <role>`, `suspend <user> --reason <text>`
  (revokes sessions and certificates), `unsuspend <user>`, `reset-password <user>` (prints a
  generated 16-character password, revokes sessions). `realms` comes in task 15.
- Tests: a certificate from the API verifies with `rustcraft-protocol` and the well-known key;
  revoked ids appear after a password change; admin commands change what the API returns.

### Task 9: Accounts in the client, without UI

  main thread with the repository's `InFlight` pattern (`client/src/network/status.rs`) or

- `--hub <url>` client flag (default `DEFAULT_HUB`), stored in the account file at login.
- When logged in, the player's name is the account's username (`CurrentPlayerProfile`), and
  its id is derived from the account UUID as the spec says (first 8 bytes, little-endian);
  logged out, today's behaviour is unchanged.
- A system renews the certificate when absent or past half its life, at start and every 10
  minutes, keeping the old one on failure.
- Tests: the account file round-trips and is 0600; the renewal decision; the name/id rule;
  `HubClient` against a tiny local HTTP stub (a `std::net::TcpListener` thread answering
  canned responses) for success and an error body.

### Task 10: The join handshake with certificates

Spec "Identity" and "Game changes" (`shared`, `server`). Wire format change: bump
`PROTOCOL_ID` to 45.

- `shared`: `ServerToClientMessage::AuthChallenge { nonce: [u8; 32], server_key: [u8; 32],
  hub: Option<String> }` (appended, pinned) sent by the server on the auth channel as soon as
  a client connects; `AuthRegisterRequest` gains `proof: Option<JoinProof>` with
  `JoinProof { certificate: Vec<u8>, certificate_signature: [u8; 64] as Vec<u8>, signature:
  Vec<u8> }` (or arrays with serde-big-array; keep bincode-friendly).
- Client (`client/src/network/setup.rs`): waits for `AuthChallenge` before sending
  `AuthRegisterRequest`; attaches a proof when logged in and the challenge's `hub` equals the
  account's hub; a hub-mode server with no proof dismisses with a clear reason ("This server
  needs a Rustcraft account: log in from the main menu.").
- Server: `server_key.ron` in the game folder (created at first start); `--auth
  <offline|hub>` and `--hub <url>`; in hub mode, fetch the well-known keys at start with
  `ureq` (cache them in `hub_keys.ron`, use the cache when the hub is unreachable, refuse to
  start when neither exists), verify the proof (certificate against the hub keys, join
  signature against the nonce and server key) and dismiss on failure with a reason; read
  `/v1/revoked` at start and hourly (in a thread) and refuse revoked ids. In offline mode
  `proof` is ignored.
- In hub mode the player's name is the certificate's name (not the requested username) and
  their `PlayerId` the spec's rule; the duplicate check is by account.
- Update every `AuthRegisterRequest` literal (see `client/src/e2e/raw_client.rs`,
  `server/tests/session.rs`, `client/src/network/cleanup.rs`,
  `server/src/network/dispatcher.rs`, `shared/src/messages/mod.rs`).
- Tests (server/tests): offline server, no proof → joins as today; hub server (test keys
  injected through a test-only constructor, no network) with a valid proof → joins with the
  certificate's name; expired certificate, wrong hub key, signature for another nonce or
  server key, revoked id → dismissed with distinct reasons; no proof → dismissed.

## Lot 3 — hosted worlds

### Task 13: Hosted world mode in the server

Spec "Hosted worlds" and "Game changes". `--realm <uuid>` (requires `--auth hub`) and the
environment variable `RUSTCRAFT_REALM_TOKEN`: the server reads `GET /v1/realms/{id}/config`
(header `Authorization: Realm <token>`) at start (refusing to start if it fails) and every 60
s in a thread; the whitelist is on and holds exactly the members, operators are the
`operator` members and the owner; `/op`, `/whitelist`, `/ban` and `/pardon` answer "Manage the
members of a hosted world from the game's Hosted worlds tab." in this mode. A member removed
while online is dismissed with "You were removed from this world.". Tests with a stub HTTP
server.

### Task 14: The realm agent

`hub/realm-agent` (binary `rustcraft-realm-agent`, member of the hub workspace), spec
"Hosted worlds" ("Agent", "Container").

- Config file (`--config`, TOML, example `hub/realm-agent.example.toml`): `socket` path,
  `image`, `memory`, `cpus`, `pids`, `base_port` (25000), `slots` (20), `max_render_distance`
  (12), `max_players` (10), `hub_url`, `stop_grace_seconds` (30), `network` (Docker network
  name, default bridge).
- Newline-delimited JSON over the Unix socket (mode 0660): requests `start`, `stop`,
  `status`, `archive`, `purge` and their responses; the realm id must be a UUID and the slot
  `< slots`; anything else is refused. `start` creates the volume `rustcraft-realm-<uuid>` if
  needed and a container `rustcraft-realm-<uuid>` from the configured image with the
  spec's limits and options (`ReadonlyRootfs`, `CapDrop ALL`, `SecurityOpt
  no-new-privileges`, user 10001, `/data` volume, `tmpfs /tmp`), ports published on
  `0.0.0.0` and `::`, the env `RUSTCRAFT_REALM_TOKEN`, and the command `--world world --port
  8000 --auth hub --hub <hub_url> --realm <uuid> --max-render-distance … --max-players …`
  plus the world settings from the request. `stop` = SIGTERM with the grace period then
  remove the container (keep the volume). `archive` renames by creating
  `rustcraft-realm-<uuid>-archived-<date>` and copying (or tags it with a label) — choose the
  simplest that works with Docker volumes and document it.
- Uses `bollard`. Unit tests for request validation and for the container spec built from a
  config and a request (no Docker needed); an ignored-by-default integration test against the
  local Docker.
- `hub/Dockerfile` target `realm-agent` and the `realm-agent` service in `compose.yaml`
  (`docker.sock` mounted, `network_mode: none`, shared socket volume with the hub).

### Task 15: Realms in the hub

Spec "Hosted worlds", "Hub API" (realm routes), "Database".

- Migration `0002_realms.sql`: `realms` (as the spec, plus `token_hash bytea`,
  `last_empty_at timestamptz`, `failed_reason text`) and `realm_members`.
- Routes of the spec's table. `POST /v1/realms` validates `name` (1–32 chars, no control
  characters) and `settings` (`seed` optional u32, `world_type`, `biome`, `game_mode`,
  `difficulty` with the server's names from task 2) and the role/quota. `start` allocates
  the lowest free slot among `--realm-slots` (default 20), refuses beyond `--max-running`
  (default 3) with `no_free_slot`, issues a realm token, asks the agent to start, and returns
  `{state: "starting", host: --realm-host, port}`. Members are added by username.
- `RealmAgent` trait with the agent client (task 14's protocol over the Unix socket at
  `--agent-socket`, default `/run/realm-agent/agent.sock`) and a fake for tests.
- A monitor task: every 5 s for `starting` worlds (status probe on the slot's status port via
  `rustcraft_protocol::status`, 60 s timeout → `failed`, agent `stop`), every 30 s for
  `running` worlds (0 players for 10 min → stop; agent status exited → `stopped`/`failed`);
  at start, reconcile the database with the agent's view.
- Archive: agent `archive`, state `archived`; a daily task asks the agent to remove archives
  older than 30 days (agent request `purge {older_than_days}`).
- `rustcraft-hub admin realms` lists worlds with owner, state, slot, players, last played.
- Tests with the fake agent and a fake status responder: create within quota, refused without
  role or over quota, start allocates a slot and returns the port, a non-member cannot start,
  idle stop after the timeout (inject the clock/durations), failed start, member management.
