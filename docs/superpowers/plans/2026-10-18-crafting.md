# Crafting Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** A 2x2 crafting grid in the inventory and a placeable crafting table with a 3x3 grid, validated by the server (issue #92).

**Architecture:** Every inventory change becomes an `InventoryAction` carried by `PlayerFrameInput`, so the server applies it in input order and the client predicts it and replays the unacknowledged ones at reconciliation, like movement. Recipes and actions live in `shared`; the floating stack, the crafting grid (slots 36..45) and the open table live in `Inventory`, which the server already sends every tick.

**Tech Stack:** Rust nightly-2026-10-01, Bevy 0.19, renet, bincode (network), RON (player saves).

**Spec:** Claude Doc « Cadrage — Crafting (#92) » (https://claude.ai/code/artifact/f90380ac-1617-40ff-9b69-0f0b93e2871d), decisions taken with the recommendations: decorative furnace (8 `Cobblestone` ring) as the first 3x3 recipe, `SprucePlanks` added, lot 1 shipped as its own PR to `main`, sneak + right click places against a table.

## Global Constraints

- `ItemId`, `BlockId`, `NetworkAction`, the messages and every new enum sent on the network are append only; each new variant gets a line in its pinning test.
- `PROTOCOL_ID` (`shared/src/constants.rs`): 1 → 2 in lot 1, 2 → 3 in lot 2. `FORMAT_VERSION` unchanged (chunk encoding of existing blocks unchanged).
- Player save files (RON) written before this work must still load: new `Inventory` fields carry `#[serde(default)]`.
- Build with `CARGO_TARGET_DIR=/home/user/Code/rustcraft/main/target` (disk is nearly full). `just check` must pass at the end of every task.
- Code style: doc comments in full sentences like the surrounding code, tests named as sentences.

## Review Focus

1. A client sends a slot id outside the inventory (e.g. 1000 or a hidden grid cell) → the server ignores the action, nothing is created. (Task 1, Task 6, Task 8 tests)
2. The inventory is closed by Escape, not E, with items in the cursor or the grid → they go back to the inventory. (Task 2: close detection from visibility, not from the key)
3. The server update arrives between a click and its acknowledgement → the click stays visible (replay). (Task 2 test)
4. The inventory is full when the grid is closed → leftovers stay in the grid/cursor (saved), never lost or duplicated. (Task 6 test)
5. A player opens a table then the table is broken or the player is far → no 3x3 craft is accepted. (Task 8 test)

## Lot 3 — recipes and the 2x2 grid

### Task 5: Recipe engine

**Files:**
- Create: `shared/src/world/crafting.rs`; Modify: `shared/src/world/mod.rs`

**Interfaces:**
- Produces:
  - `pub const CRAFTING_GRID_START: u32 = MAX_INVENTORY_SLOTS;` `pub const CRAFTING_GRID_SIZE: u32 = 3;` — grid cell (row, col) is slot `CRAFTING_GRID_START + row * 3 + col`.
  - `pub type CraftingGrid = [Option<ItemId>; 9];`
  - `pub fn match_recipe(grid: &CraftingGrid) -> Option<ItemStack>` — shaped recipes: the grid is cut to the bounding box of its filled cells and compared cell by cell to each pattern, so a pattern matches anywhere.
  - Recipes: `OakLog` → 4 `OakPlanks`; `SpruceLog` → 4 `SprucePlanks`; `OakPlanks` over `OakPlanks` → 4 `Stick`; same with `SprucePlanks` → 4 `Stick`; 2x2 `OakPlanks` → 1 `CraftingTable`; 2x2 `SprucePlanks` → 1 `CraftingTable`; 3x3 ring of `Cobblestone` with an empty centre → 1 `Furnace`.

- [ ] Failing tests: one per recipe; `a_recipe_matches_anywhere_in_the_grid`; `planks_side_by_side_make_nothing`; `an_extra_item_makes_nothing`; `an_empty_grid_makes_nothing`.
- [ ] Implement, `cargo test -p shared`, commit `feat(shared): match the crafting grid against the recipes`.
