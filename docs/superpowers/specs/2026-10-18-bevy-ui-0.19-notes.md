## 1. bevy_input_focus

### 1.1 `InputFocus` (resource)
`bevy::input_focus::InputFocus`, defined at `input_focus/lib.rs:97-154`.
* `fn set(&mut self, entity: Entity, cause: FocusCause)` (:139), `const fn get(&self) -> Option<Entity>` (:145),
  `fn clear(&mut self)` (:150), `fn from_entity(Entity) -> Self` (:125, intended for tests; it drops buffered changes).
* `FocusCause::{Navigated, Pressed}` (`gained_and_lost.rs:16-24`).
* Added by `InputFocusPlugin` (`lib.rs:267-280`), which is part of `DefaultPlugins`. At
  `PostStartup`, `set_initial_focus` (`lib.rs:327-334`) **focuses the primary window entity** when
  nothing else has focus.
* Focus changes produce `FocusGained { entity, cause }` and `FocusLost { entity }`, both entity
  events that bubble up the hierarchy (`auto_propagate`, `gained_and_lost.rs:29-56`). They are
  sent in `PostUpdate` by `process_recorded_focus_changes` (`gained_and_lost.rs:61`,
  set `InputFocusSystems::FocusChangeEvents`), so they fire on the frame of the change, after `Update`.
* Helpers: the trait `IsFocused` (`lib.rs:395`) with `is_focused`, `is_focus_within`,
  `is_focus_visible` and `is_focus_within_visible`, implemented for `World` and for the
  `IsFocusedHelper` SystemParam (`lib.rs:415-447`).

### 1.2 `InputFocusVisible` (resource)
`InputFocusVisible(pub bool)` at `lib.rs:170-176`. It is advisory: the crate itself never reads
it. It is set to `true` by Tab (`tab_navigation.rs:455`) and by list-box arrows (`ui_widgets/list.rs:162`),
and to `false` by a click (`tab_navigation.rs:409-412`, `ui_widgets/checkbox.rs:105-107`).
Show the focus ring only while it is true; feathers does this (section 7).

### 1.3 `AutoFocus` (component)
`AutoFocus` at `autofocus.rs:17-30`. An `on_add` hook calls
`InputFocus::set(entity, Navigated)` when the component is added. Use it on the first button of
a screen or dialog.

### 1.4 `InputDispatchPlugin` and `FocusedInput<M>`: how a widget receives keys
* `InputDispatchPlugin` (`lib.rs:286-309`, part of `DefaultPlugins`) adds
  `dispatch_focused_input::<KeyboardInput>`, `::<GamepadButtonChangedEvent>` and `::<MouseWheel>`
  in `PreUpdate`, in set `InputFocusSystems::Dispatch`, after `bevy_input::InputSystems`.
* `dispatch_focused_input` (`lib.rs:341-383`) **reads the `KeyboardInput` messages**. The harness
  already writes these, so the dispatch works headless. For each message it triggers
  `FocusedInput { focused_entity, input, window }` on the focused entity. If nothing has focus,
  or the focused entity was despawned, it triggers on the primary window instead.
* `FocusedInput<M>` (`lib.rs:185-200`) is an `EntityEvent` with
  `propagate = WindowTraversal, auto_propagate`. It bubbles through `ChildOf` parents and then to
  the window (`lib.rs:226-242`). Public fields: `focused_entity` (the `#[event_target]`) and
  `input: M`. The `window` field is private.
* **Propagation semantics** (`bevy_ecs-0.19.1/src/event/trigger.rs:301-314`). At each bubbling
  step the event target is **overwritten with the current entity** (`set_event_target`), so inside
  an observer `ev.focused_entity` is the entity currently being visited.
  `ev.original_event_target()` (`ecs/observer/system_param.rs:139`) returns the entity that
  actually has focus. At each step **global observers run first, then entity observers**
  (`trigger.rs:188-206`). `ev.propagate(false)` only stops the next steps, so other observers on
  the same entity still run.

```rust
use bevy::input::{keyboard::KeyboardInput, ButtonState};
use bevy::input_focus::FocusedInput;

// Entity observer on a widget: receives keys while it, or any descendant, has focus.
commands.spawn((Node::default(), TabIndex(0))).observe(
    |mut ev: On<FocusedInput<KeyboardInput>>| {
        let k = &ev.input;
        if k.state == ButtonState::Pressed && !k.repeat && k.key_code == KeyCode::Escape {
            ev.propagate(false);
            // go back ...
        }
    },
);
```

### 1.5 Tab navigation (`bevy::input_focus::tab_navigation`)
* `TabIndex(pub i32)` (`tab_navigation.rs:57-63`). A value `>= 0` takes part in Tab order, while
  `< 0` can be focused by click or code but is skipped by Tab (:5-10).
* `TabGroup { pub order: i32, pub modal: bool }` with `TabGroup::new(order)` and
  `TabGroup::modal()` (:66-99). **A `TabIndex` entity only counts if it descends from a `TabGroup`.**
* `NavAction::{Next, Previous, First, Last}` (:110-127).
* `TabNavigation` SystemParam (:158-171):
  * `fn navigate(&self, focus: &InputFocus, action: NavAction) -> Result<Entity, TabNavigationError>` (:183).
  * `fn initialize(&self, parent: Entity, action: NavAction) -> Result<Entity, TabNavigationError>`
    (:214) returns the first or last focusable entity inside the given `TabGroup` entity. Use it to
    put focus into a dialog.
* Ordering (:256-321). Inside a **modal** group, only that group's descendants are candidates.
  Otherwise every **non-modal** group is a candidate, sorted by `order` and then by `TabIndex`,
  with ties broken by tree order. Navigation wraps around. Gathering does not descend into nested
  `TabGroup`s, and modal groups are skipped entirely (:337-349).
* The group is found **only among the focused entity's ancestors**
  (`iter_ancestors`, :195-204), never the entity itself. **Do not put the focus on the
  `TabGroup::modal()` entity itself**, or Tab escapes the modal.
* `TabNavigationPlugin` (:380-389) adds:
  * A `Startup` system that attaches the observer `handle_tab_navigation` **to every
    `PrimaryWindow` entity** (:391-395). The window is spawned while `WindowPlugin` builds
    (`bevy_window-0.19.1/src/lib.rs:128-129`), so it exists in time, including in the harness.
  * `handle_tab_navigation` (:429-468). On `FocusedInput<KeyboardInput>`, when
    `key_code == KeyCode::Tab`, the state is Pressed and the event is not a repeat, it calls
    `navigate` with `Previous` if `ButtonInput<KeyCode>` reports ShiftLeft or ShiftRight pressed,
    and `Next` otherwise. It then sets `InputFocus` and `InputFocusVisible(true)`. **It relies on
    the `KeyboardInput` messages** (through `FocusedInput`) **and on `ButtonInput<KeyCode>`** for
    Shift. Both are fed by the messages the harness writes. Tab only reaches the window if no
    observer below it stopped propagation; `EditableText` lets Tab through
    (`ui_widgets/text_input.rs:145-147`).
  * If the focus has no `TabGroup` ancestor (the initial focus is the window), `navigate` returns
    `NoTabGroupForCurrentFocus`. The handler recovers by focusing `new_focus` but logs a `warn!`
    (:458-465). Setting `AutoFocus` on each screen avoids the warning.
  * `acquire_focus` observer (:355-377). An `AcquireFocus` event bubbles to the nearest ancestor
    with a `TabIndex` and focuses it. If it reaches the window first, it **clears** the focus.
  * `click_to_focus` (:397-421, behind the `bevy_picking` feature, which is on). On
    `Pointer<Press>` aimed at the original target, it sets `InputFocusVisible(false)` and triggers
    `AcquireFocus`. **So clicking a widget, or any of its children, focuses its nearest `TabIndex`
    ancestor, and clicking empty space clears the focus.** This is driven by **picking**, not by
    `Interaction`. Also, `AcquireFocus` sets `FocusCause::Navigated` even for clicks
    (:367). Only `Checkbox` and `EditableText` set `FocusCause::Pressed` themselves.

### 1.6 Directional navigation
* `bevy::input_focus::directional_navigation`. `DirectionalNavigationPlugin`
  (`directional_navigation.rs:74-80`) only initialises the resources
  `DirectionalNavigationMap` and `AutoNavigationConfig`. **Nothing reads the arrow keys or the
  gamepad: you write that system.**
* `DirectionalNavigationMap` (:248-393). Methods: `add_edge(a, b, CompassOctant)`,
  `add_symmetrical_edge`, `add_edges(&[Entity], dir)`, `add_looping_edges(&[Entity], dir)`,
  `block_edge`, `remove`, `clear`, `get_neighbor -> NavNeighbor::{Auto, Blocked, Set(e)}`.
* `DirectionalNavigation<'w>` SystemParam (:395-434):
  `fn navigate(&mut self, CompassOctant) -> Result<Entity, DirectionalNavigationError>`. It follows
  manual edges only and sets `InputFocus` itself.
* **Automatic navigation from layout lives in bevy_ui**:
  `bevy::ui::auto_directional_navigation::{AutoDirectionalNavigation, AutoDirectionalNavigator}`
  (`ui/auto_directional_navigation.rs:105-200`). Put the marker
  `AutoDirectionalNavigation::default()` on the nodes and call
  `AutoDirectionalNavigator::navigate(CompassOctant)`, which tries manual edges first and falls
  back to geometry (`find_best_candidate`). Limits (doc :51-78):
  * It is **z-index and layer agnostic**: every marked node on the same camera is a candidate,
    so a modal does not trap arrow keys.
  * Nodes need a `ComputedUiTargetCamera` with a camera (:214, :245), so a UI camera is required.
    The harness has one.
  * It skips hidden and zero-size nodes.
* The geometry is public: `bevy::input_focus::navigator::find_best_candidate(origin: &FocusableArea, dir: CompassOctant, candidates: &[FocusableArea], cfg: &AutoNavigationConfig) -> Option<Entity>`
  (`navigator.rs:144-149`), with `FocusableArea { entity, position /*centre, logical px*/, size }`
  (`directional_navigation.rs:472-476`). Also
  `auto_generate_navigation_edges(&mut map, &[FocusableArea], &cfg)` (:518).
  **Recommended:** run our own arrow-key observer that limits the candidates to the current
  container or modal group and calls `find_best_candidate`:

```rust
use bevy::input_focus::{directional_navigation::{AutoNavigationConfig, FocusableArea},
    navigator::find_best_candidate, FocusCause, FocusedInput, InputFocus, InputFocusVisible};
use bevy::math::CompassOctant;

#[derive(Component)] struct ArrowNav; // a grid or list container

fn arrow_nav(
    mut ev: On<FocusedInput<KeyboardInput>>,
    containers: Query<(), With<ArrowNav>>,
    children: Query<&Children>,
    items: Query<(&TabIndex, &ComputedNode, &UiGlobalTransform, &InheritedVisibility)>,
    cfg: Res<AutoNavigationConfig>,
    mut focus: ResMut<InputFocus>,
    mut visible: ResMut<InputFocusVisible>,
) {
    if !containers.contains(ev.focused_entity) { return; }        // current bubbling step
    let k = &ev.input;
    if k.state != ButtonState::Pressed { return; }
    let dir = match k.key_code {
        KeyCode::ArrowUp => CompassOctant::North, KeyCode::ArrowDown => CompassOctant::South,
        KeyCode::ArrowLeft => CompassOctant::West, KeyCode::ArrowRight => CompassOctant::East,
        _ => return,
    };
    let area = |e: Entity| items.get(e).ok().filter(|(t, n, _, v)| t.0 >= 0 && !n.is_empty() && v.get())
        .map(|(_, n, t, _)| FocusableArea { entity: e,
            position: t.translation * n.inverse_scale_factor(),
            size: n.size() * n.inverse_scale_factor() });
    let Some(origin) = area(ev.original_event_target()) else { return };
    let cands: Vec<_> = children.iter_descendants(ev.focused_entity).filter_map(area).collect();
    if let Some(next) = find_best_candidate(&origin, dir, &cands, &cfg) {
        ev.propagate(false);
        focus.set(next, FocusCause::Navigated);
        visible.0 = true;
    }
}
// app.add_observer(arrow_nav);
```

### 1.7 Focus and mouse clicks
* With `TabNavigationPlugin`, a click focuses the nearest `TabIndex` ancestor through picking
  (section 1.5).
* `Checkbox` sets focus on press **by itself** (`ui_widgets/checkbox.rs:100-107`), as does
  `EditableText` (`ui_widgets/text_input.rs:180`).
* `Button`, `Slider` and `RadioButton` do **not** set focus themselves. They depend on
  `TabNavigationPlugin` and a `TabIndex`.

## 2. bevy_ui_widgets (headless widgets)

`UiWidgetsPlugins` (`ui_widgets/lib.rs:60-77`) contains `PopoverPlugin, ButtonPlugin,
CheckboxPlugin, ListBoxPlugin, MenuPlugin, RadioGroupPlugin, ScrollAreaPlugin, ScrollbarPlugin,
SliderPlugin, EditableTextInputPlugin`. It is already in `DefaultPlugins`.
The crate is marked "Experimental: API likely to change substantially" (`lib.rs:5-11`).

**Every pointer interaction uses bevy_picking observers** (`Pointer<Press|Release|Click|Drag*|Cancel|Scroll>`).
**Every key uses `FocusedInput<KeyboardInput>`.** Nothing reads `Interaction`.
State is "external" (`lib.rs:13-19`): a widget emits an event, and the app (or a provided
`*_self_update` observer) writes the state component back.

Shared events:
* `Activate { pub entity: Entity }` (`lib.rs:79-85`). Does not propagate. Sent by `Button` and `MenuItem`.
* `ValueChange<T> { #[event_target] pub source: Entity, pub value: T, pub is_final: bool }`
  (`lib.rs:87-100`). Does not propagate.

Shared state components, in `bevy::ui`, `ui/interaction_states.rs`:
`InteractionDisabled` (:23, which sets the a11y node to disabled), `Pressed` (:46),
`Checkable` (:51), `Checked` (:56, which sets the a11y `toggled` state), `Selectable` (:94) and
`Selected` (:98). Hover is **not** among them. For hover, insert
`bevy::picking::hover::Hovered(bool)` (`picking/hover.rs:339`, kept up to date by
`update_is_hovered`, `picking/lib.rs:450`) or `DirectlyHovered` (:357). Both are picking-driven.

Helper: `bevy::ui_widgets::observe(observer)` (`observe.rs:177`) is a `Bundle` that attaches an
entity observer. It is handy inside `children![]`.

**Gaps:**
* No **Tabs** widget. accesskit has `Role::TabList`, `Tab` and `TabPanel` (`accesskit-0.24.1/src/lib.rs:194-196`).
  The smallest alternative is a `RadioGroup` styled as a tab bar: arrows switch tabs, and it
  sends `ValueChange<Entity>`. Override its `AccessibilityNode` with `Role::TabList` and `Role::Tab`.
* No dialog or modal widget (section 1.5 shows how to build one).
* No grid navigation. `MenuLayout::Grid` explicitly says "arrow keys are not mapped" (`menu.rs:98`).
* Known bug: `menu.rs:296-301`. In a `Row` menu, ArrowRight sets the focus and then immediately
  clears it.
* `MenuButton` requires the legacy `bevy_ui::widget::Button`, so also add
  `bevy_ui_widgets::Button`, as feathers does (`feathers/controls/menu.rs:164-174` through
  `FeathersButton`), or it will not activate.
* **No widget requires `TabIndex`.** Add `TabIndex(0)` yourself, as feathers does
  (`feathers/controls/button.rs:98`).

**What "headless" means: everything visual is ours.**
* Backgrounds, borders, images and the 9-slice frame.
* Hover (`Hovered`), pressed (`Pressed`), disabled (`InteractionDisabled`), checked (`Checked`)
  and selected (`Selected`) looks, applied by our own style systems or observers on those
  components.
* The focus ring, driven by `InputFocus` and `InputFocusVisible`.
* The slider thumb position: read `SliderValue` and `SliderRange::thumb_position(value)` and set
  `Node.left` as a percentage.
* The scrollbar thumb colours. Its size and position are computed by the widget.
* The list-box active-row outline, from `ActiveDescendant`.
* The text cursor and selection colours (`TextCursorStyle`), plus a placeholder.

## 3. Text editing

**Bevy 0.19.1 has a built-in single-line editable field.** Use it instead of `bevy_simple_text_input`.

* The component is `bevy::text::EditableText` (`text/editing.rs:97-164`). It requires
  `TextLayout, TextFont, TextColor, LineHeight, FontHinting, EditableTextGeneration`, and
  `EditableTextInputPlugin` registers `Node, TextNodeFlags, ContentSize, TextScroll` as further
  requirements (`ui_widgets/text_input.rs:528-531`).
  Public fields: `editor: parley::PlainEditor<TextBrush>`, `pending_edits: Vec<TextEdit>`,
  `cursor_width: f32` (relative to font size, default 0.2), `cursor_blink_period: Duration`
  (default 1 s), `max_characters: Option<usize>`, `visible_lines: Option<f32>` (default
  `Some(1.)`), `visible_width: Option<f32>`, `allow_newlines: bool` (default false).
  The defaults therefore make it single-line.
* API: `EditableText::new(initial)` (:169), `value() -> parley::SplitString` (call
  `.to_string()`, :190), `queue_edit(TextEdit)` (:195), `clear()` (:259), `is_composing()` (:269).
  To replace the text at runtime, follow the feathers pattern: `queue_edit(TextEdit::SelectAll)`
  then `queue_edit(TextEdit::Insert(s.into()))` (`feathers/controls/number_input.rs:224-227`).
* `TextEdit` (`text/text_edit.rs:26-`) has the variants Copy, Cut, Paste, `Insert(SmolStr)`,
  Backspace, BackspaceWord, Delete, DeleteWord, `Left/Right/WordLeft/WordRight/Up/Down/TextStart/TextEnd/HardLineStart/HardLineEnd/LineStart/LineEnd(bool extend)`,

* The cursor and selection are drawn **only if the entity has `TextCursorStyle`**
  (`text/cursor.rs:7-37`: `color, selection_color, unfocused_selection_color, selected_text_color`)
  and **only while it has `InputFocus`** (`bevy_ui_render-0.19.1/src/text.rs:19-90`).
* **Missing** (the module doc says so, `editing.rs:57-67`): placeholder, undo / redo, validation,
  password masking, a11y integration, and **submit handling**. So:
  * Submit on Enter: add an entity observer on the field (sketch below).
  * Placeholder: a sibling or overlay `Text`, shown while `value().is_empty()`.
  * a11y: add `AccessibilityNode(accesskit::Node::new(Role::TextInput))` ourselves.
  * Escape from a field: `EditableText` stops its propagation, so a "back" observer on an ancestor
    does not see it. Put the Escape handler **on the field entity itself**: entity observers still
    run after the global one stopped propagation (section 1.4).
* Timing trap: characters and Enter that arrive in **the same frame** are all dispatched in
  `PreUpdate`, but the characters are applied in `PostUpdate`, so an Enter observer reading
  `value()` would miss them. This is robust:

```rust
use bevy::text::{EditableText, EditableTextSystems, TextCursorStyle};
use bevy::text::LineBreak;

#[derive(Component)] struct SubmitRequested;
#[derive(EntityEvent)] pub struct Submit { pub entity: Entity, pub value: String }

fn spawn_field(commands: &mut Commands) -> Entity {
    commands.spawn((
        EditableText { max_characters: Some(32), ..default() },
        TextLayout { linebreak: LineBreak::NoWrap, ..default() },
        TextCursorStyle::default(), TabIndex(0),
        Node { width: px(300), ..default() },
    ))
    .observe(|mut ev: On<FocusedInput<KeyboardInput>>, q: Query<&EditableText>, mut commands: Commands| {
        let k = &ev.input;
        if k.state != ButtonState::Pressed || k.repeat { return; }
        let e = ev.focused_entity;                     // this field
        match k.key_code {
            KeyCode::Enter if q.get(e).is_ok_and(|t| !t.is_composing()) => {
                ev.propagate(false);
                commands.entity(e).insert(SubmitRequested);
            }
            KeyCode::Escape => { /* cancel / back */ }
            _ => {}
        }
    })
    .id()
}

fn emit_submits(q: Query<(Entity, &EditableText), With<SubmitRequested>>, mut commands: Commands) {
    for (e, t) in &q {
        commands.entity(e).remove::<SubmitRequested>();
        commands.trigger(Submit { entity: e, value: t.value().to_string() });
    }
}
// app.add_systems(PostUpdate, emit_submits.after(EditableTextSystems));
```

## 4. UiScale and pixel art

* `bevy::ui::UiScale(pub f32)` is a resource that defaults to 1.0 (`ui/lib.rs:120-133`).
  It is multiplied into each UI root's `ComputedUiRenderTargetInfo.scale_factor = camera.target_scaling_factor() * ui_scale`
  (`ui/update.rs:153-166`).
  * It scales `Val::Px` and other absolute lengths, and the text size in px. Text is laid out and
    rasterised at that scale factor (`ui/widget/text.rs:297-310,421`), so **text stays crisp**.
  * `Val::Percent`, `Vw`, `Vh` and `FontSize::Vh` etc. (`text/text.rs:487-497`) are not affected.
* **Picking still hits:** `ui_picking` converts the pointer to physical pixels
  (`ui/picking_backend.rs:133-141`), and the node rects are in physical pixels.
  `ui_focus_system` (legacy `Interaction`) uses `Window::physical_cursor_position`
  (`ui/focus.rs:148,205`). `Slider` and `EditableText` divide by `UiScale` explicitly
  (`ui_widgets/slider.rs:318,495`, `text_input.rs:191`). The harness's `center_of` returns
  `UiGlobalTransform.translation`, which is physical (`e2e/locator.rs:306-312`), so it stays
  correct under any `UiScale`.
* Following the window height:

```rust
fn ui_scale_from_window(window: Single<&Window, With<PrimaryWindow>>, mut scale: ResMut<UiScale>) {
    // the UI is designed for 720 logical px of height; snap so that pixel art stays even
    let s = (window.height() / 720.0 * 2.0).floor().max(1.0) / 2.0;   // 0.5 steps; use .floor() for integers
    if scale.0 != s { scale.0 = s; }
}
```

* Image sampling:
  * `ImageNode` has **no per-node sampler**. Its fields are `color, image, texture_atlas, flip_x,
    flip_y, rect, image_mode, visual_box` (`ui/widget/image.rs:18-44`).
  * The sampler belongs to each `Image` asset (`Image::sampler`, or `ImageLoaderSettings`), or is
    set globally by `ImagePlugin::default_nearest()`. The client already sets that globally
    (`main.rs:91`, `ui/golden.rs:66`, `e2e/harness.rs:139`), so UI images are **not blurred** at
    1.5.
  * A non-integer scale with nearest sampling gives uneven texel widths (some screen pixels
    double, others not), so prefer integer, or at least 0.5-step, scales.
  * For frames, use `NodeImageMode::Sliced(TextureSlicer { border, center_scale_mode,
    sides_scale_mode, max_corner_scale })` (`ui/widget/image.rs:158-176`;
    `bevy_sprite-0.19.1/src/texture_slice/slicer.rs:15-23`).
  * For pixel fonts: `TextFont { font_smoothing: FontSmoothing::None, .. }` (`text/text.rs:404,1183-1190`).
    `TextFont::font_size` is now a `FontSize` enum (`text/text.rs:392,487`), not an `f32`.

## 5. Accessibility: roles and labels, read back in tests

* `bevy::a11y::AccessibilityNode(pub accesskit::Node)` is a component with `Deref` and `DerefMut`
  (`a11y/lib.rs:225-240`). `AccessibilityPlugin` (:275-283) only adds resources. The tree is
  pushed to the OS by `bevy_winit`. **The component itself is plain ECS data and is readable
  in-process without winit.**
* **Bevy does not re-export accesskit** (`a11y/lib.rs:35-42`). Add `accesskit = "0.24"` to the

* Roles: the widgets set them through `#[require(AccessibilityNode(Node::new(Role::X)))]` (see
  the table in section 2). For our own nodes, insert
  `AccessibilityNode(accesskit::Node::new(Role::Dialog))` and so on.
* Labels:
  * `bevy::ui::prelude::AccessibleLabel(pub String)` / `AccessibleLabel::new("Play")`
    (`ui/accessibility.rs:185-211`, exported from `ui/lib.rs:57`). An `on_insert` hook writes
    `set_label` into the `AccessibilityNode`.

    `bevy_ui::widget::Button`, `ImageNode` and `Label`** (`ui/accessibility.rs:86-171`), not for

## 6. Picking vs Interaction, and the headless harness (most important for e2e)

* bevy_ui_widgets uses **picking only** (`Pointer<…>` observers in every widget file) and
  **`FocusedInput` for keys**. `bevy_ui`'s `ui_focus_system` (`Interaction`) still runs in
  `PreUpdate` (`ui/lib.rs:173-176`), but only on entities that have `Interaction`, which comes
  with the legacy `Button`. Both systems can coexist during the migration.
* Picking in `DefaultPlugins`: `DefaultPickingPlugins` = `PointerInputPlugin + PickingPlugin +
  InteractionPlugin` (`picking/lib.rs:285-293`). `UiPickingPlugin` is added by `UiPlugin`
  (`ui/lib.rs:178-183`). `UiPickingSettings::require_markers` defaults to false
  (`ui/picking_backend.rs:47-53`), so every node is pickable.
* **Where the mouse input comes from:** `bevy::picking::input::mouse_pick_events`
  (`picking/input.rs:121-201`, in `First`) reads **only `MessageReader<WindowEvent>`**: the
  variants `WindowEvent::CursorMoved`, `WindowEvent::MouseButtonInput` and `WindowEvent::MouseWheel`.
  * It does **not** read `Window::cursor_position()`.
  * It does **not** read the standalone `MouseButtonInput`, `CursorMoved` or `MouseWheel` messages.
  * The press position is the last `CursorMoved` position, cached in a `Local` (:72, :102).
  * In this codebase, only `bevy_winit` writes `WindowEvent` (`bevy_winit-0.19.1/src/system.rs:137,313`).
* **So the current harness (`client/src/e2e/input.rs:92-114`) produces no picking at all.** It
  calls `Window::set_physical_cursor_position` and writes `MouseButtonInput` messages, which feeds
  only `Interaction`. No `Pointer<Press/Click>` fires, so ui_widgets buttons, sliders and
  checkboxes, `Hovered`, click-to-focus, `EditableText` caret placement and `ScrollArea` wheel
  scrolling would all be dead in e2e tests. Keyboard paths (`FocusedInput`, Tab) do work, because
  they read `KeyboardInput` messages and `ButtonInput`.
* **Fix (small, additive):** keep the current writes, which still drive `Interaction` during the
  migration, and **also write the `WindowEvent` messages**:

```rust
use bevy::window::{CursorMoved, WindowEvent};

fn move_cursor(&mut self, physical: Vec2) {
    let window = self.window();
    let scale = self.world().get::<Window>(window).unwrap().scale_factor();
    self.world_mut().get_mut::<Window>(window).unwrap().set_physical_cursor_position(Some(physical.as_dvec2()));
    self.world_mut().write_message(WindowEvent::CursorMoved(CursorMoved {
        window, position: physical / scale /* logical */, delta: None,
    }));
}
// in click_with, per state:
self.world_mut().write_message(MouseButtonInput { button, state, window });
self.world_mut().write_message(WindowEvent::MouseButtonInput(MouseButtonInput { button, state, window }));
// in scroll: also write WindowEvent::MouseWheel(MouseWheel { .. })   // From impls: bevy_window event.rs:585,669,681
```

  The pointer target is `RenderTarget::Window(WindowRef::Entity(window))` normalised against the
  primary window (`picking/input.rs:134-139`). It matches the cameras while they render to
  `WindowRef::Primary`. During `capture` the harness retargets the cameras to an `Image`
  (`e2e/capture.rs:35,53`), so a click in the middle of a capture would miss; do not click there.
  The existing sequence of one move frame, then a press frame, then a release frame is right for
  picking: the hover map is built in `PreUpdate` and `Click` fires on release over the same entity.
* **Keyboard in the harness:**
  * `press()` / `key_down()` send `Key::Unidentified` as the logical key (`e2e/input.rs:44-61`).
    That is fine for ui_widgets (Button, Slider, List, Radio, Tab all match `key_code`).
  * It is **not fine for `EditableText`**, which matches `logical_key` and reads modifiers from
    `ButtonInput<Key>`. Map `Enter → Key::Enter`, `Escape → Key::Escape`, `Backspace →
    Key::Backspace`, the arrows → `Key::ArrowX`, `Tab → Key::Tab`, `ShiftLeft → Key::Shift` and so on.
  * `type_text` already sends `Key::Character` with `text`, which works with `EditableText`.
* `Hovered` changes need picking, so the same `WindowEvent::CursorMoved` fix applies to hover visuals.

## Recommendations for Rustcraft

**Adopt (all already compiled in, no Cargo feature changes):**
1. `bevy::input_focus`: `InputFocus`, `InputFocusVisible`, `AutoFocus`, `FocusedInput<KeyboardInput>`
   observers for every key handling (Enter / Escape / arrows), and `TabNavigationPlugin` (add it
   explicitly) with `TabGroup::new(n)` per screen and `TabGroup::modal()` per dialog.
2. `bevy::ui_widgets`: `Button`, `Checkbox`, `Slider`, `RadioGroup` (also as Tabs), `ListBox` for
   world and server lists, `ScrollArea` + `Scrollbar` + `ScrollIntoView`, and `observe(..)`.
   Wrap them in our own theme and widget layer that inserts `TabIndex(0)`, `Hovered`,
   `AccessibleLabel` and the pixel-art visuals.
3. `bevy::text::EditableText` (with `TextCursorStyle`) for every text field, plus our own
   `Submit` event (deferred to after `EditableTextSystems`), placeholder overlay and
   `Role::TextInput`. **Remove `bevy_simple_text_input`.**
4. Arrow keys: our own observer around `navigator::find_best_candidate`, limited to the focused
   container or modal (sketch in section 1.6). Use `DirectionalNavigationMap` only for overrides.
   Avoid the global `AutoDirectionalNavigator`, which is z-index agnostic and would escape modals.
5. Modal dialogs:
   * A root with `TabGroup::modal()`, `GlobalZIndex` and a full-screen backdrop child with
     `TabIndex(-1)`, so a click on the backdrop keeps the focus inside the modal.
   * `AutoFocus` on the first control, or `TabNavigation::initialize(root, NavAction::First)`.
   * Escape handled by an entity observer on the dialog root, and also on its text fields.
   * On close, restore the saved previous focus.
6. `UiScale` driven by the window height, snapped to 0.5 or 1.0 steps. Keep
   `ImagePlugin::default_nearest()`, and use `NodeImageMode::Sliced` for frames.
7. a11y: add `accesskit = "0.24"` and a `Locator::role(Role, label)` that queries `AccessibilityNode`.

**Avoid:** `bevy_feathers` as a dependency, the `ui_widgets` Menu for the main menus (it is tied to
popups that close on focus loss, `MenuButton` needs the legacy `Button`, and it has the Row bug),
`AutoDirectionalNavigation` without layer filtering, and mixing the legacy `Interaction` with
the widgets on the same entity.

**Risks for the headless e2e harness:**
1. **Picking needs `WindowEvent` messages.** Without the change in section 6, every pointer
   interaction with the new widgets silently does nothing in tests. Make this change first and
   prove it with one test that clicks a `ui_widgets::Button` and sees `Activate`.
2. The logical keys in `press()` must be real `Key` values for `EditableText`
   (Enter / Backspace / Escape / arrows / Shift).
3. Text value timing: edits are applied in `PostUpdate`. One key per frame (the harness today) is
   fine; the submit should still be deferred (section 3).
4. Remove the harness code specific to simple_text_input (`TextInputInactive`, `TextInputValue`,
   the `TextInputInner` locator case).
5. The first Tab while the window holds focus logs a `warn!` (`tab_navigation.rs:458-465`); use
   `AutoFocus` per screen.
6. While cameras target the capture image, picking does not hit (`e2e/capture.rs:35-53`). Only
   click outside captures.
7. bevy_ui_widgets is experimental: pin `bevy = "=0.19.1"`, or expect churn in 0.20.
8. The golden screenshots will change with the redesign and with `UiScale`. Regenerate them on
   purpose.
